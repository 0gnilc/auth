Architecture review

gnilc-auth-core 分层结构分析与重新设计

日期：2026-06-19 · 范围：gnilc-auth-core 及其认证、授权、Web adapter、Spring Boot 装配 seam。

结论

存在分层缺陷。 当前 gnilc-auth-core 不是纯 core module，而是把授权核心、Servlet adapter、Web 自动配置和一部分认证 Web SPI 放进同一个 Maven module。抽象层与 Web 实现层的 seam 被压扁，导致 leverage 和 locality 都下降。

CONTEXT.md:21-41 明确：访问上下文是环境无关输入；Servlet request、MQ message 等执行环境对象应由 adapter 翻译；访问拒绝处理是当前执行环境动作。

当前分支处于大迁移中：旧 com.gnilc.authz/authn 包大量删除，新 com.gnilc.auth.* 包出现。报告基于当前工作区。

当前分层诊断

  • Artifact seam 错位：gnilc-auth-core 的 pom.xml:15-19 直接声明 spring-boot-starter-web，即使 optional，也让 core artifact 带 Web 语义。
  • 自动配置泄漏：AutoConfiguration.imports:1 指向 ServletAuthenticationAutoConfiguration，core artifact 对外表现为 Web starter。
  • 认证 core 缺位：ServletAuthenticationHandler.java:10-25 直接以 ServletAuthenticationContext 为接口输入。
  • 授权 adapter 留在 core：ServletAuthorizationAutoConfiguration.java:29-69 注册 Servlet resolver、adapter、filter 和 denied handler。
  • 访问目标语义未闭合：ServletAccessContextAdapter.java:38-42 把 HTTP method 放入 attributes，RbacRequiredPermissionsProvider.java:44-46 又只按 target identifier 匹配。

3. 问题分析：浅 module 与错位 seam

问题 A：core artifact 同时是 Web starter

Strong

Problem：调用方引入 core module 时，必须同时理解 Servlet filter 顺序、Boot 条件装配、Web denied handler 等实现事实，接口与实现几乎等宽。

Evidence：pom.xml:15-19、AutoConfiguration.imports:1、ServletAuthenticationAutoConfiguration.java:29-59。

Deletion test：删除 Web 自动配置不会让授权核心复杂度消失，只会把 filter 注册复杂度移动到 adapter/starter；因此这不是 core 应承担的深度。

问题 B：认证缺少环境无关 core

Strong

Problem：ServletAuthenticationHandler 的接口直接接收 ServletAuthenticationContext，认证 module 的 seam 只能存在于 Web 层。

Evidence：ServletAuthenticationHandler.java:10-25、ServletAuthenticationContext.java:12-41、ServletAuthenticationFilter.java:52-71。

Impact：消息、任务、CLI 场景若要复用认证行为，只能复制 Servlet-specific 规则，locality 变差。

问题 C：授权 core 与 Servlet adapter 共居

Strong

Problem：AccessContext 的领域语言已经正确，但 generic seam 的第一个 adapter 直接放在同一 artifact，导致 seam 的物理位置不清。

Evidence：AccessContext.java:7-10 表示执行环境对象应先由 adapter 翻译；但 ServletAccessContextAdapter.java:20-45 和 ServletAuthorizationFilter.java:43-62 仍在 core module。

Impact：未来增加 MQ/task adapter 时，core artifact 会继续膨胀，深度下降。

问题 D：Principal 桥接链路过长且浅

Worth exploring

Problem：认证结果到授权身份的链路是 AuthenticationResult → DefaultAccessPrincipal → HttpServletRequest → AccessIdentityResolverDelegate → AccessIdentity → AccessContext，每一步都暴露额外接口知识。

Evidence：DefaultAccessPrincipal.java:20-84、DefaultAccessPrincipalHolder.java:23-33、AdminSessionAccessIdentityResolverDelegate.java:21-35。

Impact：DefaultAccessPrincipal 是薄 DTO，却成为跨 module 契约；这是浅 module 的典型迹象。

问题 E：AccessTarget qualifier 语义未闭合

Worth exploring

Problem：AccessTarget 已定义 qualifier 用于 HTTP method 等变体，但 Servlet adapter 写入 attributes，RBAC required provider 又忽略 qualifier。

Evidence：AccessTarget.java:7-10、ServletAccessContextAdapter.java:38-42、RbacRequiredPermissionsProvider.java:44-46。

Impact：目标匹配规则散落在 adapter 和 provider 之间，locality 不足。

问题 F：RBAC Web enable seam 过粗

Worth exploring

Problem：ServletRbacAuthorizationAutoConfiguration 听起来是启用授权，实际会扫描整个 RBAC 包并注册 mapper，seam 名称与实现影响范围不一致。

Evidence：ServletRbacAuthorizationAutoConfiguration.java:10-15。

Impact：调用方无法只拿 RBAC provider；controller、dao、cache、exception advice 会一起进入应用。
