# 代码命名与结构重构标准

供后续按需采用的通用参考，不自动成为项目执行规则。使用时结合当前业务契约、语言惯例和已有架构决策确定具体约定。

## 1. 范围与目标

- 从当前代码中的具体问题出发，说明要消除的歧义、重复定义、调用负担或职责分散。
- 命名与结构重构保持业务规则、权限、数据含义和用户可见行为；需要改变这些内容时，作为明确的需求变更处理。
- 只处理有当前使用依据的问题，不为假设的未来场景增加类型、接口、状态或兼容路径。

## 2. 数据类型按职责区分

- 按数据含义、约束、使用责任和明确的契约隔离要求决定类型是否独立；字段相同或经过不同调用层，都不足以单独决定合并或拆分。
- 同一契约内，没有独立职责的重复表示优先共用。真实持久化记录与对外契约需要隔离时，即使字段相同也分别保留。
- 对面向输出的纯查询，优先直接填充所需结果类型；关联或派生字段由查询拥有者补齐。只用于复制字段的中间对象不作为固定步骤。
- 持久化类型仍参与新增、修改或业务判断，不代表每条查询都必须经过它。业务处理已读取记录时，可以直接映射响应，不为省去映射再查询一次。
- 继承表达同一种数据的扩展，并保持原有字段含义和约束；字段重复本身不构成继承依据。
- 创建时间、更新时间、删除标记等字段按实际生命周期选择，不为套用基类补齐无用途的字段。

## 3. 输入、表单与状态

- 输入仅包含该操作允许调用者提交的数据。当前执行者身份来自可信上下文，系统生成或计算的数据由系统确定；选择目标所需的 ID 可以是输入。
- 请求类型由请求边界定义。表单与请求的字段、含义和约束一致时共用；存在文件对象、本地时间或编辑中间值等差异时，单独定义表单类型并在提交边界转换。
- 编辑值与保存中、上传中等流程状态分别表达。共享状态放在拥有该事实和生命周期的位置，避免多个页面各自维护副本。
- 输入、查询、结果与表单类型是否需要独立，先判断职责，再决定名称。

例如，`ArticleInput` 可同时用于编辑与提交；若表单持有 `File`，请求需要图片对象键，则 `ArticleFormValues` 有独立存在的理由。

## 4. 字段契约与转换

- 同一业务字段在含义、范围和精度不变时，各层尽量使用一致的类型；传输格式差异由明确的序列化或接入边界处理。
- 前端声明必须符合实际 JSON，包括必填、缺省、可空和枚举范围。类型声明不会自动转换运行时数据。
- 超过 JavaScript 安全整数范围的整数采用无损传输方式；精确十进制计算使用十进制类型或库，不能先转换成不精确的数值再尝试恢复。
- 精度校验、业务舍入和显示补位是不同操作；小数位、范围及舍入方式由字段所属业务决定，外部协议的特殊精度留在接入边界。
- 转换必须有语义、协议或控件约束依据，避免页面反复执行同一字段的字符串与数值转换。展示所需的有损转换不回流业务计算。

## 5. 完整职责与协作边界

- 先确定需要共同保证的规则和结果，再决定类、文件与方法的拆合。必须一起完成的流程由一个明确的拥有者负责。
- 保持同一业务的高内聚，不按客户端、读写标签或代码长度机械拆分；相似代码也不意味着两个业务必须共用规则。
- 封装应让调用者少理解一组规则、步骤、状态或协议细节。仅换名转发且没有独立边界作用的包装应移除。
- 接口用于当前真实的多实现协作、模块契约或框架要求，不默认给每个类配一个接口，也不因只有一个实现就自动删除接口。
- 在拥有一致性责任的位置处理事务、幂等、失败顺序和恢复；临时状态按所属生命周期清理。

例如，两个内容业务可以各自拥有编辑规则，同时共用独立的图片上传状态管理；共享机制不要求合并业务流程。

## 6. 工具、共享代码与参数

- 业务规则放在所属业务内。稳定且独立于调用业务的共享能力，才放入应用公共层或跨应用库。
- 静态方法、纯函数或多个调用者并不足以证明它是通用工具。先检查已有能力，再决定新增封装。
- 参数表达方法实际需要的信息：只需编号就传编号，需要记录参与业务处理就传记录；不为缩小字段范围另造同义类型。
- 参数对象应表达一个明确概念，不以减少参数个数为唯一理由。
- 可选配置服务于已存在的差异，默认值由能力拥有者统一定义。

## 7. 名称表达语义

- 按业务事实、职责或行为命名，结合所在模块、文件、参数和返回类型判断是否足够清楚。
- 上下文已消除歧义时使用简洁名称；离开上下文仍会误导时增加限定。名称不必逐字复述实现细节。
- 业务名称不携带无关的客户端或技术标签；真实身份、协议和接入职责仍应明确表达。
- 后缀在同一项目中保持单一职责。`Bo`、`Dto`、`Vo` 的具体约定由项目确定；`Row`、`Data`、`Model`、`Result`、`Operations` 等泛称不能替代职责判断。
- 前后端对齐业务含义和字段契约，不强制相同后缀。命名空间已有的业务限定不重复书写。
- 查询条件可用 `Query`，操作输入可用 `Input`，确有差异的表单编辑值可用 `FormValues`；上下文已清楚表达用途时不叠加后缀。

例如，后端 `SalesSummaryVo` 与前端 `SalesApi.Summary` 可以表达同一响应契约；`SalesApi.SummaryQuery` 表达查询条件。名称不同不影响字段对齐，也不构成新增转换的理由。

## 8. 交付与验收

- 按受影响业务能力的完整可用和语义一致交付，同步处理实际受影响的调用、类型、字符串绑定、配置和文档，不要求所有相关文件都改动。
- 替换后移除旧实现和失效引用。兼容路径必须有当前契约依据；涉及外部消费者或历史数据时，明确迁移范围。
- 按变化选择足够的格式、静态检查、类型检查和行为验证。测试实际责任主体，不以模拟结果代替待验证的行为。
- 验收同时确认：原有契约保持，声明的设计目标有证据，关联修改与必要验证完成。记录未覆盖的范围。
- 以歧义减少、职责集中、重复定义消除或调用负担降低说明收益，不用改名数量、代码行数或测试数量代替。
